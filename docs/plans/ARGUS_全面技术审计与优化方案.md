## 1. 产品目标与第一性原理

ARGUS
的核心价值不是"抓取更多内容"，而是在有限注意力和计算成本下，持续发现高价值信息、识别事件关系、过滤噪声，并提供可信、及时、可追溯的知识入口。

因此系统质量应由六个问题决定：

1.  **发现完整性**：应该采集的内容是否被发现？失败时能否识别缺口并补采？
2.  **内容真实性**：原文、作者、发布时间、转载关系是否准确？
3.  **价值判断**：评分是否稳定、可解释、经过样本校准？
4.  **关系正确性**：重复材料是否去重，不同事实是否误合并？
5.  **榜单有效性**：榜单反映真实关注度/价值，还是采集覆盖和信源数量？
6.  **阅读效率**：用户能否快速理解重点、查看证据、跟进变化和沉淀知识？

关键原则：**上游数据质量决定下游上限；榜单、日报和 UI
都不应该掩盖采集缺失或归并不确定性。**

## 2. 整体架构审计

### 2.1 当前架构

-   Web：React Router SSR，负责页面和用户交互。
-   API：Fastify，负责站点接口、管理接口、MCP、RSS/公开 API、媒体出口。
-   Worker：采集、模型分析、事件归并、热度计算、日报、运维任务。
-   PostgreSQL：业务数据与任务状态。
-   pg-boss：持久化任务队列与定时任务。
-   `packages/backend`：采集、内容、编辑、事件、发布、媒体、通知等领域逻辑。
-   `packages/contracts`：前后端共享契约。
-   `modules/aihot`：行业镜像扩展模块。

### 2.2 优点

1.  Web 不直接承担抓取与模型调用，职责隔离正确。
2.  API 统一作为数据读取和写入边界，SSR 通过 HTTP 访问 API。
3.  Worker 任务持久化，较适合长时间运行的采集与模型工作。
4.  模块通过 server module socket 注册，AIHOT 不必侵入引擎核心。
5.  发布投影 `publications` 将复杂分析结果转为稳定读取模型。
6.  模型 receipts、预算、任务运行记录和恢复任务体现了成本及可靠性意识。

### 2.3 问题与建议

**A. `packages/backend` 领域过宽**

目前同一 package 包含
sources、content、editorial、events、publication、reports、media、providers、operations、notify
等大量领域。文件拆分本身不等于边界清晰，尤其事件分组、发布投影、任务调度之间存在较多跨域调用。

建议保持模块化单体，不急于微服务化，但明确依赖方向：

-   `sources` 只负责获取与标准化来源数据。
-   `content` 负责原始材料、版本、媒体和内容提取。
-   `editorial` 负责价值判断、翻译、摘要和标签。
-   `events` 负责 Fact / Story 身份及关系。
-   `publication` 负责面向用户的读模型。
-   `ranking`（可从现有 hot 模块逐步抽出）只消费已确认的证据。
-   `operations` 负责运行状态、告警、恢复、备份和保留策略。

禁止 publication 反向修改采集状态；禁止 UI 直接依赖数据库内部表结构。

**B. 任务执行与领域逻辑耦合**

建议引入清晰的任务输入/输出契约：任务携带对象
ID、revision、规则版本、触发原因；执行结果记录成功、跳过、可重试失败、永久失败及部分成功。不要让每个
job 自己发明状态语义。

**C. 缺少显式的数据质量层**

建议在业务链路中增加统一质量状态：

`observed → normalized → validated → analyzed → grouped → published`

每一步都记录输入版本、输出版本、失败原因、完整性和处理时间。这样能区分"没采到""采到了但无法解析""模型失败""归并未完成"和"被策略过滤"。

## 3. 信源采集逻辑审计

### 3.1 当前实现判断

README 描述的当前策略是双轨：

-   自有信源：44 个指定账号，`track:learning`。
-   行业新闻与发布：AIHOT 行业镜像。
-   RSS 类型框架保留，但当前没有配置 RSS 源。
-   X：FxTwitter 优先，SocialData 兜底；付费调用有预算限制。
-   Worker 通过每分钟调度器安排到期信源，另有 RSS 探活、X
    改名跟踪、图标刷新等任务。

该策略对个人情报产品是合理的：自有关注源和行业聚合源的目标不同，不应强行使用一套评分和采集策略。

### 3.2 主要风险

**问题 1：请求成功不等于采集完整。**

HTTP 200、解析成功，只能证明一次请求成功。不能证明：

-   平台分页已经读完；
-   账号最新内容没有超出 API 窗口；
-   平台限流期间没有漏掉时间段；
-   转帖、引用、长文和媒体已完整获取；
-   上游只返回部分数据时系统能够识别。

优化：每个 source 保存
`cursor/watermark`、`last_seen_published_at`、`oldest_seen_at`、分页终止原因、返回数、去重数、解析失败数。为每个平台建立补采窗口和缺口告警。

**问题 2：不同平台时间字段语义不统一。**

统一定义：

-   `published_at`：平台原始发布时间。
-   `source_updated_at`：源内容更新时间。
-   `discovered_at`：ARGUS 首次发现时间。
-   `fetched_at`：最近一次抓取时间。
-   `observed_at`：作为讨论证据被观察到的时间。

所有时间均保存
UTC，展示时按用户时区转换。禁止将抓取时间填充为发布时间来参与趋势计算，除非显式标注为估算值。

**问题 3：采集适配器缺少统一的可观测指标。**

每个 Adapter 输出统一结果：

``` ts
type CollectionResult = {
  status: "complete" | "partial" | "failed" | "not_modified";
  fetched: number;
  created: number;
  updated: number;
  duplicates: number;
  rejected: number;
  pagesRead: number;
  hasMore: boolean;
  oldestPublishedAt?: string;
  newestPublishedAt?: string;
  nextCursor?: string;
  retryAfterMs?: number;
};
```

**问题 4：信源健康度应从"请求健康"升级为"数据健康"。**

建议健康度由以下维度共同决定：

-   请求成功率；
-   实际内容产出；
-   发布时间水位是否前进；
-   分页是否完整；
-   内容解析成功率；
-   连续空结果次数；
-   最近成功采集距今时间；
-   是否存在待补采缺口。

**问题 5：平台适配器的成本和稳定性需要量化。**

FxTwitter 免费优先、SocialData 兜底是合理的，但应统计每个平台每 1000
条有效材料的成本、延迟、成功率和内容完整率，而不是只看请求费用。

### 3.3 建议的采集架构

`Source Registry → Scheduler → Platform Adapter → Raw Capture → Normalizer → Dedup → Article Upsert → Processing Queue`

原始抓取结果应保留必要的来源元数据和内容哈希，便于重放、排查解析器变化和补偿处理。对于版权和隐私敏感内容，应限制原始数据留存期限。

## 4. 评分逻辑审计

### 4.1 当前实现

当前新闻轨：

-   评分范围 0--100。
-   模型两次评分，平均分作为结果。
-   T1 门槛 60、T1.5 门槛 65、T2 门槛 76。
-   未入选但达到理解分数下限的内容仍可生成更完整的标题、摘要和推荐理由。

学习轨：

-   `hit / edge / miss` 映射为 90 / 60 / 20。
-   只在边界档 `edge` 进行第二次判断。
-   `inherit` 轨继承上游选择，不重复评分。

提示词定义了五轴：实质份量、信息增量、证据强度、共振面、可用性，并按内容类型配置权重。

### 4.2 值得保留

1.  评分与是否精选分离。
2.  不把来源名称、信源等级直接交给模型，降低名气偏差。
3.  不同内容类型采用不同权重。
4.  对 Prompt Injection 有明确不可信输入边界。
5.  Prompt 版本写入分析记录，可追溯历史结果。
6.  有评分评估脚本和人工 Gold 样本工具。

### 4.3 核心问题

**问题 1：两次评分均值不等于评分可靠性。**

两次调用可能使用同一模型、同一提示词、同一输入，因此错误可能高度相关。平均分只能降低部分随机波动，不能证明评分准确。

建议记录： - 两次原始分数； - 分差； - 是否跨越门槛； -
模型、模型版本、Prompt 版本； - 最终决策； - 人工复核标签。

门槛附近的样本应优先复核，而不是所有内容一律增加模型调用。

**问题 2：信源等级门槛可能引入选择偏差。**

同一内容价值，T1 60 分入选、T2 76
分才入选。这是编辑策略，不是内容价值本身。

建议保留原始价值分数，另计算编辑优先级：

`Editorial Priority = f(Intrinsic Value, Source Confidence, Freshness, User Preference)`

其中信源可信度不应简单等价于来源名气；要结合官方身份、原始证据、历史准确率和内容类型。

**问题 3：五轴模型缺少结构化可审计结果。**

当前模型只输出
`attentionScore`，五轴只在模型内部计算。这样无法判断分数低究竟是证据不足、信息增量低还是受众相关性低。

建议在离线评估模型中输出五轴和理由；生产模型可以仍保持单字段输出以节省
token，但定期抽样执行解释性评估。

**问题 4：评分校准不能只依赖固定阈值。**

建立 Gold
Dataset，按内容类型、信源层级、平台、语言和时间分层抽样。评估： -
人工评分与模型评分的 MAE； - 入选 Precision / Recall； -
门槛附近误判率； - 两次评分分差分布； - 不同模型版本的分布漂移； -
不同来源之间的同价值公平性。

建议把阈值配置版本化，阈值调整必须有离线评估报告和回滚能力。

**问题 5：模型应判断事件价值，而非文章表现。**

现有提示词已明确要求评价事件本身，这个方向正确。后续需要进一步防止同一事件的多篇报道分别评分后，导致大量重复内容消耗精选名额。

建议：先识别强事件/内容类型，再评分；归并后由事件层聚合价值，但仍保留文章自身质量和证据强度。

## 5. 内容去重与事件归并审计

### 5.1 当前模型

-   Article：材料身份。
-   Fact：单个具体事实/变化。
-   Story：事件及其进展。
-   Embedding + 词面召回生成候选。
-   LLM 对候选关系进行判断。
-   低相似度合并要求第二模型确认。
-   人工修正优先，不允许模型随意覆盖。
-   Composite 内容不直接成为事件根或桥接材料。
-   Story 合并后保留 alias，旧地址继续解析。
-   不确定但持续相关的事件可以建立 related link。

这是本项目最重要的差异化能力之一，建议保留。

### 5.2 必须区分三个问题

  层级           问题                 典型例子
  -------------- -------------------- --------------------------------------
  Article 去重   是否同一条内容       X 原帖与同一原帖的镜像 URL
  Fact 归并      是否同一个具体变化   某模型发布、价格变化、功能上线
  Story 合并     是否同一持续事件     某公司发布模型后又更新能力和开放入口

三个层级的阈值、证据和错误成本不同，不能用统一 cosine 阈值代替。

### 5.3 主要优化点

**问题 1：候选召回漏召回比模型误判更难发现。**

模型只在召回候选中判断。若候选没有被召回，再强的 LLM 也无法纠正。

建议分别测量： - Recall@K； - 候选集平均规模； - 正确候选排名； -
无候选但实际应归并的比例； - 召回耗时与模型成本。

增加多路召回：规范 URL、平台原生
ID、实体/资产指纹、标题词面、Embedding、时间窗口。每路召回记录来源和贡献。

**问题 2：错误合并与错误拆分的代价不对称。**

错误合并会污染整个事件历史、代表内容、热度和日报；错误拆分则会让同一事件重复出现。

建议对 Story 合并设置更高门槛，优先"保持分离 +
相关链接"，只有根事件一致且有充分证据才合并。

**问题 3：Fact 需要更强的证据约束。**

Fact 不应只是 LLM 生成的结构化标题。建议每个 Fact 必须有： - subject /
action / object； - occurred_at（允许 unknown）； - supporting article
IDs； - evidence span 或引用片段； - claim confidence； - contradiction
state； - first_seen / last_seen。

**问题 4：人工修正需要形成评估闭环。**

人工操作应记录修改前后关系、原因、操作者、时间、规则版本。每次修正都成为回归样本，定期重跑归并评估。

**问题 5：防止事件链式漂移。**

现有设计已经明确限制通过发展链无限扩张
Story，这是正确的。建议将"同一事件""事件发展""背景相关""因果相关"区分为不同关系，不要只保留一个
related 概念。

### 5.4 推荐归并流程

`Identity Rules → Multi-channel Recall → Candidate Ranking → LLM Relation Judgment → High-risk Second Review → Transactional Membership Write → Story Consolidation → Quality Evaluation`

## 6. AIHOT 行业镜像逻辑审计

### 6.1 当前实现

`modules/aihot` 读取三个上游地址：

-   `/api/site/hot`
-   `/api/v1/hot-topics`
-   `/api/v1/items?mode=selected&window=7d`

机制包括： - 15 分钟定时读取； - ETag / If-None-Match； -
Retry-After； - 保存上游快照； - 复制上游精选结果，不重复调用模型； -
写入本站 Article / Analysis / Publication； -
通过本站图片代理重新签名图片地址； - 旧内容到期后清理； -
上游失败时保留旧数据，不直接清空。

这个模块化方向合理，也避免重复支付模型成本。

### 6.2 P1：不同接口的快照可能不在同一时间点

`pass.ts` 分别读取
hot、topics、selected。每个读取函数在请求失败时可能沿用各自上一次的
answer。

因此可能出现： - hot 是 10:00 的快照； - topics 是 09:45 的快照； -
selected 是 10:00 的窗口。

`rankingOf()` 再通过 story ID 关联主题榜和热榜。

这意味着虽然数据库写入是在一个事务中完成，但事务一致性不等于上游快照一致性。

**建议：** - 每个快照保存 `computedAt`、上游版本、抓取时间和 ETag。 -
定义最大允许时间偏差，例如 15 分钟。 - 超出偏差时标记
`mixed_snapshot`，不要把它展示成完全一致的榜单。 - 尽量使用上游统一
snapshot/version；若无此能力，明确显示各接口数据时间。 -
对排名和封面缺失区分"上游没有"与"本次接口未更新"。

### 6.3 P1：分页上限可能导致静默截断

`upstream.ts` 设置 `MAX_PAGES = 6`。当第六页后仍有 `hasMore`
时，函数会返回已读取内容，并把 ETag 置空。

这能避免错误地将不完整分页结果标记为完整，但没有明确把"达到分页上限"作为异常状态上报。

建议： - 返回
`complete: boolean`、`truncated: boolean`、`stopReason`。 -
达到页数上限必须产生告警。 -
不应把不完整窗口与完整窗口使用同一种状态。 -
统计上游总量、实际读入量和入库量。

### 6.4 P1：镜像内容的授权与署名边界需要明确

代码注释指出上游条款要求保留 attribution；`provenance()`
保存了上游地址、归属和条款信息，但注释同时说明前台不展示上游名称与标识。

此外，`POLICY_HEADERS`
只是请求时声明本镜像方的商业使用策略，并不等于上游已经授予书面商业授权。

建议： 1.
明确上游条款允许的使用范围：个人、商业、再发布、图片代理、摘要改写。 2.
对要求署名的字段，在前台提供可见且可追溯的 attribution。 3.
将"请求声明""上游响应声明""实际授权凭证"分开存储。 4.
没有书面授权时，不要把请求头声明误当成授权证明。 5.
记录条款版本、检查时间、授权状态和撤回机制。 6.
对上游内容和本站原创内容进行清晰区分。

这是产品合规边界，不是单纯技术实现问题。

### 6.5 P2：镜像保留期与上游窗口语义不完全一致

`retireMirrored()` 使用本站首次 `discovered_at`
作为保留期起点。这样内容从本站首次镜像起保留 N
天，而不是按上游发布时间或上游 7 天窗口截止时间保留。

建议明确策略： - 如果目标是本站保留 7 天：当前做法可以接受，但应命名为
local retention。 - 如果目标是严格同步上游窗口：应以
`upstream_published_at` 或上游窗口边界计算。 -
对被日报引用的内容保留引用依赖，但不要让历史日报无限阻止所有关联材料清理。

### 6.6 镜像优化目标

镜像不是"复制数据"这么简单，建议引入独立的镜像状态机：

`read → validate → snapshot-align → ingest → publish → reconcile → retire`

每轮记录： - 上游接口状态； - 快照时间差； - 分页完整性； -
上游条目数； - 新增、更新、跳过、撤回数量； - 代表图关联成功率； -
授权/署名状态。

## 7. 热榜与榜单逻辑审计

### 7.1 当前热度算法

`events/hot.ts` 使用： - 最近 48 小时； - 24 小时半衰期； -
按独立参与者计数； - 同一参与者在一个窗口内不因重复采集而增加热度； -
使用来源发布时间/观察时间证据，而非单纯抓取时间； - 区分 editorial /
signal； - 对采集落后的来源进行 behind 处理； - 与 6
小时前比较计算趋势。

这比"文章数量排序"合理得多。

### 7.2 主要问题和建议

**问题 1：独立参与者定义会直接决定热度。**

代码会按社区作者、信源 signal group、owner entity 或 source ID
识别参与者。该机制合理，但必须持续检查实体归属和分组配置是否准确。

建议建立 participant audit： - 原始来源； - participant key； -
归并理由； - 是否同一组织； - 是否存在一个主体被拆成多个参与者； -
多个主体被错误合并的比例。

**问题 2：热度和内容价值必须分开。**

热度高不代表内容有价值；高价值官方公告可能讨论人数少。首页精选、热榜和日报应分别呈现价值、讨论热度和新鲜度，不要用一个指数代替。

**问题 3：来源覆盖不完整时，趋势可能失真。**

当前已有 behind source
处理，这是重要设计。建议进一步把榜单覆盖度展示出来，例如： -
当前参与计算的信源数； - 落后信源数； - 可比较参与者数； -
与上一窗口相比的覆盖变化。

趋势应允许 `unknown`，不要为了展示完整而硬算涨跌。

**问题 4：上游榜单与本站榜单必须清晰区分。**

当前 AIHOT
模块直接继承上游排名，并在页面文案中披露来源，这是正确的。建议在所有
API、MCP、日报和分享卡片中也保持相同披露，避免不同出口让用户误以为是本站独立计算。

### 7.3 推荐未来榜单体系

  榜单          排序依据                         目的
  ------------- -------------------------------- ----------------------
  行业热榜      独立参与者、时效衰减、讨论增量   发现行业正在发生什么
  AI 价值精选   内容价值、证据强度、用户偏好     发现真正值得读的内容
  学习榜        可复用程度、实践价值、知识增量   提升个人 AI 能力
  趋势榜        同一主题/事件的持续增长          发现长期趋势
  官方动态      官方源、发布时间、重要程度       追踪一手信息

榜单必须明确窗口、时区、去重口径和数据覆盖范围。

## 8. 镜像与媒体资源管理

### 8.1 当前优点

-   图片使用独立媒体模块。
-   图片下载经过 guarded fetch。
-   有 SSRF 地址检查、响应体大小限制、超时和重定向控制。
-   使用 sharp 处理尺寸与格式。
-   有 in-flight 去重和本地缓存。
-   有上游图片流量预算。

### 8.2 优化建议

1.  将媒体资源抽象为 `asset`，不只存 URL；增加源 URL、内容
    hash、MIME、尺寸、来源、版权状态、首次抓取时间、最后访问时间。
2.  相同图片跨 URL 可通过内容哈希去重；URL 规范化只用于初步去重。
3.  图片缓存增加总容量上限、LRU/TTL 清理、磁盘占用监控。
4.  生成缩略图时统一尺寸规范，避免页面重复请求不同尺寸导致重复转码。
5.  对 SVG、GIF、动画图像和超大图片继续保留安全限制。
6.  媒体资源与原始文章生命周期分离，防止文章删除后孤儿文件持续占用磁盘。
7.  对第三方图片使用和再分发增加来源/授权标记。

## 9. 数据库审计

### 9.1 当前数据模型

核心表覆盖： - sources / fetch_runs； - articles / article_revisions /
article_discoveries； - analyses / editorial_overrides； -
publications； - facts / stories / fact_articles / story_signals； -
hot_rankings / story_heat_hourly； - reports / report_revisions； -
receipts / budgets； - 以及任务、管理、运营和镜像状态相关表。

这是一个较完整的业务模型。

### 9.2 主要建议

**A. 明确事实表、过程表和读模型**

-   articles：原始材料与当前版本。
-   article_revisions：内容历史。
-   analyses：模型判断历史。
-   facts/stories：事件知识模型。
-   publications：读模型。
-   reports：日报/周报等生成产物。

避免为了页面方便把所有业务状态都写进 publications。

**B. 检查数据生命周期**

建议按数据类别制定保留策略：

  数据             建议策略
  ---------------- --------------------------------
  原始响应         短期保留，按平台与版权策略控制
  Article 元数据   长期保留
  正文/媒体        按价值、授权和访问情况保留
  分析结果         保留版本和关键审计信息
  事件与人工修正   长期保留
  任务日志         按周期归档
  模型请求/响应    脱敏后按审计需要保留
  榜单快照         保留必要历史，用于趋势回放

**C. 迁移管理**

文件树中存在重复编号，例如多个
0056、0057、0086、0090。若执行器使用完整文件名排序并记录文件名，未必构成运行错误，但容易造成迁移管理混乱。

建议迁移编号改为唯一递增 ID，增加： - migration checksum； -
执行时间； - 执行版本； - 可重复执行保护； - 生产环境迁移前检查； -
大表索引使用 `CONCURRENTLY` 时的非事务执行标记。

**D. 索引和查询计划**

已有针对发布时间、筛选、资产
key、搜索等索引优化。下一步应基于真实慢查询和
`EXPLAIN (ANALYZE, BUFFERS)` 验证，而不是盲目增加索引。

重点压测： - 首页精选时间线； - 全部情报组合筛选； - 关键词搜索； -
Story 详情； - 热榜计算； - Fact / Story 候选召回； - 后台内容诊断； -
大量文章的 retention。

**E. PostgreSQL 数值类型**

当前 `db.ts` 将 int8 和 numeric 转为 JS number，并注释说明当前值低于
`2^53`。建议对可能无限增长的金额、计数和 ID
继续做边界约束；尤其成本和高精度数值不要在业务层无条件转成浮点数。

## 10. API 与后端审计

### 10.1 优点

-   API 使用 Fastify，路由有清晰分组。
-   有统一错误响应。
-   日志对 Authorization、Cookie 做脱敏。
-   访问日志避免记录 query string。
-   有私有访问门禁、内部令牌和 SSR API 代理。
-   出站请求集中在 guarded fetch 中，具备 SSRF 防护。

### 10.2 需要验证的点

**A. `trustProxy` 信任边界**

`apps/api/src/app.ts` 无条件设置 `trustProxy: true`，而 Web 服务通过
`TRUST_PROXY` 环境变量控制信任代理。

建议 API 也采用明确的可信代理配置，或确保 API
只能由内部网络访问。必须验证： - API 端口是否对公网开放； -
反向代理是否覆盖/清洗转发头； - IP 限流是否能被伪造 X-Forwarded-For
绕过。

**B. API 权限矩阵**

对所有路由建立权限矩阵：匿名、登录用户、管理员、内部 SSR、MCP
客户端、Agent Token。逐项验证读取、写入、导出、媒体访问和管理操作。

**C. 统一超时与取消**

请求级 AbortSignal 应贯穿 DB 查询、上游 fetch
和下游处理。模型调用和采集任务则使用任务级超时，不应被 Web
请求生命周期意外取消。

**D. 限流分层**

按身份、IP、API
Token、路由成本和目标上游分别限流。登录、搜索、媒体代理、MCP、采集推送应有不同预算。

## 11. 前端与 UI 视觉审计

### 11.1 当前实现评价

前端使用 React 19、React Router SSR、Tailwind CSS。`app.css`
有完整语义化设计 token： - 暖纸白背景； - 墨色文字； - 低饱和强调色； -
统一圆角体系； - 明确响应式断点； - 深色模式； - 中文字体回退。

页面包含首页、全部、热点、日报、主题、收藏、Agent、后台管理等。首页使用首屏视觉和
HomeBoard，热点页使用主榜卡片、热度曲线、参与者等信息。

整体视觉方向与 ARGUS 的水墨编辑风定位一致，建议保留，不建议突然改成普通
SaaS 后台风格。

### 11.2 需要优化的不是"换皮"，而是信息架构

**A. 首页信息优先级**

首页建议严格按用户决策顺序组织： 1. 今天最重要的 1--3 件事； 2.
热点变化； 3. 个人关注作者的新内容； 4. AI 学习精选； 5. 完整时间线。

避免首页同时承担太多入口，导致首屏注意力分散。

**B. 内容卡片应显示数据可信度**

建议卡片按内容类型显示： - 原始平台与作者； - 发布时间； -
首次发现时间； - 一手/转述； - 事件归属； - 是否存在多源证据； -
评分或热度的含义。

**C. Story 详情页应强调时间线和证据**

事件详情建议： - 事件摘要； - 最新进展； - 时间线； - 关键 Fact； -
证据来源； - 不同报道之间的观点差异； - 关联事件。

不要只展示模型生成的长摘要。

**D. 榜单视觉要区分热度与价值**

热榜显示参与者和讨论趋势；精选显示价值与推荐原因；学习榜突出可复用知识。避免多个页面都使用同样的排名卡片，用户却不知道排序差异。

**E. 响应式与可访问性**

本轮未执行真实浏览器视觉回归，建议补充： - 375px 手机； - 768px 平板； -
1280px 笔记本； - 1440px 桌面； - 1920px 宽屏； - 深色模式； -
键盘操作； - 屏幕阅读器标签； -
长中文标题、超长作者名、无封面、加载失败、空列表等状态。

**F. 前端数据状态**

统一 loading / empty / partial / stale / error
状态。尤其镜像榜单数据过期时，应展示"数据更新于何时"，不能只靠旧缓存继续显示正常状态。

## 12. 工程质量、部署与安全

### 12.1 Docker 构建上下文需要优先验证

Dockerfile 在 `npm ci` 前复制各 workspace 的 package.json，其中包含
`modules/github/package.json`，而当前仓库存在
`modules/aihot/package.json`。需要核实模块目录是否与 Dockerfile
预复制清单同步。

建议构建前自动检查所有 workspace package.json 均已进入 Docker build
context，并执行干净缓存构建。

### 12.2 配置校验

`config.ts` 中整数配置使用 `parseInt`，布尔值按字符串 `"true"`
判断。建议使用 Zod 或等价 Schema 在启动时一次性校验： - 数值上下界； -
URL 格式； - Secret 长度； - 环境组合； - 代理地址； - 数据目录权限； -
预算配置。

错误应在启动阶段明确失败，而不是运行到对应任务才报错。

### 12.3 安全基线

继续保留 guarded fetch、SSRF
检查、日志脱敏和私有访问控制。进一步验证： - SSRF DNS rebinding
与重定向链； - 内网代理绕过； - 图片解析器资源消耗； - MCP 工具权限； -
管理员 Session 绑定与过期； - CSRF； - 密码尝试限流； -
备份加密与恢复演练； - 依赖漏洞与 SBOM； - 容器非 root 运行（当前
Dockerfile 已使用 node 用户）。

### 12.4 可观测性

建议统一记录： - traceId / jobId； - sourceId / articleId / factId /
storyId； - revision / promptVersion / ruleVersion； -
模型供应商、模型、耗时、token、成本； - 采集完整性； -
任务重试与失败分类； - DB 查询耗时； - 页面缓存命中率； -
媒体缓存命中率； - 榜单快照时间和覆盖率。

## 15. 必须建立的验收指标

  领域     指标               建议目标/验收方式
  -------- ------------------ ----------------------------------------
  采集     采集完整率         对可验证平台窗口做抽样对账，目标 ≥ 98%
  采集     发布时间水位延迟   按平台采集周期设 SLO
  去重     同材料重复率       Gold Set 验证，目标 ≤ 1%
  评分     精选 Precision     人工标注集验证，初始目标 ≥ 85%
  评分     精选 Recall        按内容类型分层，不以单一总值掩盖弱项
  评分     双评分分差         监控均值、P90 和跨门槛率
  归并     事件误合并率       高优先级指标，目标 ≤ 1%
  归并     事件漏合并率       按 Gold Set 评估，逐步降低
  榜单     数据新鲜度         展示快照时间及覆盖率
  镜像     分页完整率         完整窗口必须 100% 读完
  镜像     快照时间偏差       超过配置阈值必须标记
  API      P95 响应时间       按路由建立独立 SLO
  Worker   任务成功率         区分重试成功和最终失败
  UI       核心页面体验       Playwright 视觉与交互回归

这些数值是建议的起始验收目标，不是对当前系统表现的测量结果。需要先跑出现状基线，再正式设定
SLO。

## 16. 最终建议：什么该保留、什么该改

### 坚决保留

-   Web / API / Worker 三进程。
-   PostgreSQL + pg-boss。
-   Article / Fact / Story 三层事件模型。
-   Publication 读模型。
-   receipts / budgets / Prompt 版本化。
-   AIHOT 独立镜像模块。
-   guarded fetch 与 SSRF 防护。
-   人工归并修正优先机制。
-   当前水墨编辑风视觉方向。

### 优先修改

1.  镜像多接口快照一致性。
2.  镜像分页完整性与截断告警。
3.  Docker workspace 构建清单。
4.  信源完整性和漏采补偿。
5.  评分模型校准与价值/优先级分离。
6.  归并 Gold Set 与误合并度量。
7.  热榜覆盖度和趋势可信度。
8.  API 可信代理边界。
9.  迁移编号与数据生命周期。

### 暂时不要做

-   不要为了架构整洁就拆成微服务。
-   不要直接换数据库。
-   不要一上来重写评分模型。
-   不要把所有文章都送给大模型做归并。
-   不要把热度、价值和推荐优先级合并成一个分数。
-   不要为了 UI 视觉变化推翻现有设计语言。
-   不要在没有 Gold Dataset 的情况下大幅调整评分阈值。
